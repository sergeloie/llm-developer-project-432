# ИИ-генератор карточки товара


[![hexlet-check](https://github.com/sergeloie/llm-developer-project-432/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/sergeloie/llm-developer-project-432/actions)

Соберите бэкенд-сервис, который принимает документы поставщиков в форматах pdf, docx и
xlsx, строит по ним поисковый индекс и генерирует черновик карточки товара — с
указанием источников, списком недостающих данных и уровнем уверенности. По пути
освоите LLM-клиент с ретраями, строгий контракт результата на Pydantic, разбор
офисных документов и чанкинг, локальные эмбеддинги с pgvector и гибридный поиск,
цитирование с проверкой источников, учёт стоимости вызовов, метрики генерации и
защиту от инъекций через документы и утечки персональных данных.

Учебный проект Хекслета: https://ru.hexlet.io/programs/llm-developer

Сервис обещает не публикуемую карточку, а **прослеживаемую**: каждая характеристика
указывает на фрагмент, который её подтверждает, а то, чего в документах нет,
становится явным отсутствующим полем, а не выдуманным значением. Всё остальное в
этом README следует из этого обещания.

---

## Стек

- Java 21, Spring Boot 4, Gradle
- PostgreSQL 17 с pgvector — хранение и гибридный поиск
- Temporal — длительные операции с гарантированными повторами
- Spring AI — обращения к локальной OpenAI-совместимой модели
- Apache PDFBox и Apache POI — разбор документов

## Что нужно установить

| Что | Версия | Зачем |
|---|---|---|
| JDK | 21 | сборка и запуск |
| Docker Desktop | любой свежий | PostgreSQL, pgvector и Temporal |
| Локальный OpenAI-совместимый сервер | любой | генерация и эмбеддинги |

Сервер модели должен быть запущен **до** первого запроса. Подойдёт LM Studio или
Ollama. Нужны три модели:

| Роль | Модель | Почему именно она |
|---|---|---|
| Основная | `qwen/qwen3.5-9b` | генерация черновиков |
| Служебная | `qwen/qwen3-4b-2507` | ревью, классификация, проверка инъекций, оценка |
| Эмбеддинги | `text-embedding-embeddinggemma-300m` | 768 измерений, ровно столько же в колонке |

Список моделей не расширяемый и без запасных вариантов: отсутствующая модель валит
запрос, а не тихо ухудшает результат. Обоснование — в
[ADR-0006](docs/adr/0006-only-official-instruct-models.md).

## Установка

```bash
git clone https://github.com/sergeloie/llm-developer-project-432.git
cd llm-developer-project-432

cp .env.example .env      # и правьте порты, если они заняты
docker compose up -d      # PostgreSQL с pgvector и Temporal
./gradlew bootRun
```

Сервис поднимется на `http://127.0.0.1:8080`. Проверьте, что он готов:

```bash
curl http://127.0.0.1:8080/health/ready
# {"status":"UP","checks":{"database":{"status":"UP"},"vectorExtension":{"status":"UP","version":"0.8.7"}}}
```

> Все адреса в `.env` и в примерах — `127.0.0.1`, а не `localhost`. На Windows
> `localhost` разрешается сначала в `::1`, и сервер, слушающий только IPv4, отвечает
> ошибкой, в которой ничего не сказано про адресацию. Разбор этого — в
> [ADR-0007](docs/adr/0007-loopback-address-pinned-to-ipv4.md).

### Что лежит в `.env`

Файл читается дважды: Docker Compose читает его сам, а приложение импортирует его
как properties-источник. Поэтому в нём только строки `KEY=value` и комментарии
`#` — иначе два читателя не согласятся.

Переменные, которые чаще всего приходится менять, — `PG_PORT`, `TEMPORAL_PORT`,
`TEMPORAL_UI_PORT` и `CARD_DB_URL`: последняя обязана указывать на тот же порт, что и
`PG_PORT`. Полный список с пояснениями — в [`.env.example`](.env.example).

Приложение читает каждую настройку через `${CARD_*:default}` в
`src/main/resources/application.yml`, так что переменная окружения перекрывает
значение по умолчанию, а экспорт переменной в сессии перекрывает и файл.

## Путь за пятнадцать минут

```bash
# 1. Загрузить документ. Ответ 202 и идентификатор — разбор идёт отдельно.
curl -X POST -F "file=@data/blender_passport.pdf" http://127.0.0.1:8080/documents
# {"id":"doc-...","state":"new",...}

# 2. Дождаться, пока документ станет искомым. state станет indexed.
#    rejected означает, что документ прочитать не удалось, и несёт причину.
curl http://127.0.0.1:8080/documents/doc-...

# 3. Заказать карточку по этому документу. Ответ 202 сразу.
curl -X POST -H "Content-Type: application/json" \
  -d '{"documentIds":["doc-..."],"productHint":"блендер"}' \
  http://127.0.0.1:8080/jobs

# 4. Дождаться состояния awaiting_human — человек должен решить.
curl http://127.0.0.1:8080/jobs/<jobId>

# 5. Принять решение. Карточка появится в поле result.
curl -X POST -H "Content-Type: application/json" \
  -d '{"decision":"approve"}' http://127.0.0.1:8080/jobs/<jobId>/decision

curl http://127.0.0.1:8080/jobs/<jobId>
```

Состояния идут `new → parsing → indexed`, либо `rejected` с причиной. Джоба идёт
`pending → retrieving → generating → reviewing → awaiting_human`, а затем
`approved` или `rejected`.

## HTTP API

| Метод и путь | Что делает |
|---|---|
| `GET /health/live` | процесс жив |
| `GET /health/ready` | база отвечает, расширение pgvector активно |
| `POST /documents` | загрузить документ (`multipart/form-data`, поле `file`) |
| `GET /documents/{id}` | состояние документа и число фрагментов |
| `GET /documents/{id}/chunks` | сами фрагменты — то, что будет искаться |
| `POST /cards` | черновик по готовому тексту, синхронно |
| `POST /cards/outcome` | то же с вердиктом ревью и числом попыток |
| `POST /jobs` | асинхронная генерация: по тексту, по документам или по обоим |
| `GET /jobs/{id}` | состояние джобы; после решения — карточка в `result` |
| `GET /jobs/{id}/sources` | фрагменты, которые модель видела, с метками |
| `POST /jobs/{id}/decision` | `{"decision":"approve"\|"reject"}` |

`POST /jobs` отвечает `409`, если названный документ ещё не в состоянии `indexed`, и
перечисляет состояние каждого: это отказ на входе, а не джоба, которая через три
минуты сообщит, что работать было не с чем.

`POST /cards` — синхронный путь для текста, который уже есть. Он возвращает черновик
сразу и не требует человека; `POST /jobs` нужен, когда источник — документ.

## Тесты

```bash
./gradlew test            # весь набор, кроме живых вызовов модели
./gradlew test -PliveModel # включить и их: нужен запущенный сервер модели
```

Набору нужны Docker и сеть для Testcontainers. Собственный процесс Temporal для
тестов поднимается автоматически, сервер модели — нет: поэтому набор по умолчанию не
платит за генерацию и не ждёт её.

## Метрики

```bash
./gradlew metrics        # дешёвый набор по умолчанию
./gradlew metrics -Pfull # все документы эталонного набора
```

Харнесс идёт тем же путём, что и сервис: регистрация, разбор, чанкинг, эмбеддинг,
поиск, сборка контекста, генерация. Отчёт о качестве и стоимости — в
`build/reports/metrics/`. Нужен запущенный сервер модели и поднятый compose.

## Последний прогон (приёмка 2026-10-05)

Полный набор (`./gradlew metrics -Pfull`), модели `qwen/qwen3.5-9b`,
`qwen/qwen3-4b-2507`, `text-embedding-embeddinggemma-300m`. Отчёт:
`build/reports/metrics/run-1791227072149.md`.

| метрика | среднее |
|---|---|
| совпадение характеристик | 0.200 |
| точность цитирования | 0.095 |
| поддержка источниками (оценка модели) | измерена на 3 из 5 документов |

| документ | итог |
|---|---|
| `blender_passport.pdf` | карточка сходится с эталоном полностью (12/12) |
| `blender_kp.docx` | карточка не назвала ни одного артикула из трёх |
| `kettle_spec.xlsx` | то же: ни одного артикула из трёх |
| `kettle_manual.pdf` | к человеку: единственный фрагмент исключён как инъекция, генерировать не из чего |
| `boiler_scan.pdf` | отказ разбора (скан без текстового слоя) — ожидаемо, измерять нечего |

**Стоимость одной карточки — 0.000000000000**: модели локальные и бесплатные,
цены в настройках нулевые. Разбивка по задачам видна в `model_calls`
(`GROUP BY tier`: 9 вызовов main, 8 utility за прогон), арифметика при
ненулевых ценах доказана `CostCalculatorTest`.

**Самая слабая метрика — точность цитирования (0.095).** Причина: карточка
ссылается одним чанком на всё (`C1` × 12 считается одной хорошей ссылкой, а
не двенадцатью — так задумано), а имена характеристик модели не совпадают с
именами эталона, из-за чего часть ссылок вообще не резолвится. Отдельно
найдено и уже исправлено живьём: модель писала метку цитаты (`"Power": "C1"`)
вместо значения — контракт теперь отправляет такое на переделку
(`ResultContract`: ссылка вместо факта), после чего паспорт блендера сошёлся
12/12. Следующий шаг — то же расхождение имён на КП и спецификации.

## Устройство проекта

- [CONTEXT.md](CONTEXT.md) — глоссарий предметной области. Карточка, фрагмент,
  недостающее поле, ссылка на источник, инъекция.
- [docs/adr/](docs/adr) — семь записанных решений с обоснованием: почему обычный SQL,
  почему локальная модель, почему Temporal, почему у workflow нет песочницы, кто
  владеет контрактом ответа, почему только официальные instruct-модели, почему
  `127.0.0.1`.
- `src/main/java/com/carddraft/` — код. `documents` разбирает, `embeddings` и `search`
  ищут, `agents` формулирует промпты и хранит типы, которыми обмениваются с моделью,
  `context` собирает и проверяет контекст, `trust` экранирует ввод, `temporal`
  выполняет длительные операции, `routers` — транспорт.

## Что сервис не делает

- Не публикует карточку. Черновик всегда ждёт человека, и это состояние
  `awaiting_human`, а не успех.
- Не распознаёт сканы. PDF без текстового слоя получает отказ с причиной, а не пустой
  результат.
- Не выдумывает недостающее. Поле, которого нет в источниках, попадает в
  `missingFields`.
- Не доверяет модели на слово. Каждая ссылка проверяется: фрагмент должен
  существовать **и** быть в том контексте, который модель видела.
